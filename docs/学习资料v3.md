### 一个很关键的发现：分数是怎么算的

平台给的 E = 2691.795422。反算：1 / 2691.795422 = **0.3715 ms**——正好是我们那一版单次查询的耗时。
说明 **E 约等于「每秒能跑多少次查询」**。所以：

- 把查询从 0.389 ms 压到 0.130 ms，E 就从 2691 涨到约 7600。
- 想要 4600 分，单次查询必须 **≤ 217 µs**；想要 10000 分，要 **≤ 100 µs**。

这条推算是我们自己从一次真实评分里反推出来的，不是文档写的——文档里的公式值域只有 0~1，和 2691 对不上。

## 1.2 事务：为什么一个客户端反而简单

正常数据库要处理「多人同时改同一行」，所以要锁、要多版本（MVCC）。
这题限定单机单进程单客户端、同时最多一个显式事务 → **不存在并发冲突**。
事务只剩两件事：**别丢**（提交过的崩溃后还得在）、**别脏**（没提交的一点都不能留）。

实现：BEGIN 记下文件当前位置；事务里每条语句只追加日志、不打 COMMIT 标记；COMMIT 写一条 COMMIT 标记并刷盘一次；ROLLBACK 按 undo 表倒回去再把文件截断。

## 1.3 WAL 与 git 的类比——你的理解需要修正一处

你写：「效仿 git 每提交一次就留一个完整记录，出问题可以回到先前分支回溯，这跟崩溃后重启类似」。

**像的地方**：两者都靠「记录完整」来判断一个状态是否成立。

**关键差别**（这处要改，否则评审会认为没抓到点）：

|        | git                  | 数据库 WAL           |
| ------ | -------------------- | ----------------- |
| 目的     | **保留所有历史**，随时回退到任一版本 | **只决定最近一次提交算不算数** |
| 未完成的东西 | 会留在工作区，可继续           | **整段丢弃**，当作没发生    |
| 判据     | 有 commit 对象 + 引用指向它  | 日志里有 COMMIT 标记    |

准确讲法：「日志只往后追加、从不修改；每条记录带校验码；事务最后一条是 COMMIT 标记；恢复时把没有 COMMIT 的整段丢掉」。**它不是回退到旧版本，而是决定哪一段算数。**

这正好解释了题目要求的那句话——**「未提交事务不能部分生效」**：没打 COMMIT 的事务，它的记录压根不会生效，不存在「生效了一半」的情况。

## 1.4 内存：为什么会差一个数量级

你写「843 MB 数据但内存只有 85 MiB，这个数量级差距是要攻坚的重点」——**判断正确**。

原理：内存里只放「目录」，不放「内容」。

- 每行只记：在文件里的位置（8 字节）+ 长度（4 字节）+ 存活位（1 bit）
- 主键到行号的索引表（约 19 字节/行）
- 真正的 512 字节向量留在文件里，查询时按位置读

所以 288 万行约 100 MB 元数据；843 MB 内容不进内存。

## 1.5 查询为什么能快 3 倍

原路径：每行都拷一份 128 维向量 → 全排序 10000 条。
新路径：① 只算距离不拷贝；② 用有界堆只保留前 K；③ 预算内的表把向量放进 32 字节对齐的连续内存（arena），直接喂 SIMD；④ 两线程各扫一半再归并。
目前 130 µs 里：扫描约 80~100 µs（理论下限 71 µs，因为要读 5.12 MB）、解析约 10 µs、协议与序列化约 10 µs。

**过滤查询**更快（65 µs）：先只读每行尾部那一行 cache line（64 字节）判断等值，命中了才读 512 字节向量。

## 1.6 错误码

失败时返回 {"ok":false,"error":{"code":"duplicate_key","message":"..."}}。
公开题包里 error_codes 是空对象，驱动只查「code 非空」；但**正式题包一旦冻结映射表**，码对不上就整条用例挂。
我们的做法：内部细码在输出层集中做**别名表**（unsupported_* → unsupported_sql，no_such_table / duplicate_key / dimension_mismatch 保持），以后改口径只改一张表。

你写的「错误码处理也比较难，因为题包是空对象，冻结后会导致码对不上，所以我们用别名表统一映射」——**理解正确**，可以原样用。
