### Q3 你的批注 ⚠️ 有一处技术表述要改

你说：「效仿 git 的日志，把日志接入后，用 commit 进行数据恢复」。

- **git 的日志不是 WAL**。git 是不可变对象库 + 引用指针；数据库 WAL 是「只追加、带校验、以提交标记为可见性边界」。
- 更准确的讲法：**「日志只往后追加、从不修改；每条记录带校验码；事务最后一条是 COMMIT 标记；恢复时没有 COMMIT 的整段丢弃」**。
- 这个区别很重要，因为**「未提交事务不能部分生效」正是靠这个机制实现的**，讲错就等于没理解。
- （我的理解是我消防git的日志是效仿它每提交一次就留一个完整记录的这种结构，这样以后要是代码出现问题就可以回到先前提交的分支回溯，我认为这个跟我们的崩溃后重启类似，我们在突然崩溃后也可以通过读取需要的日志commit来回溯到可用的版本。）

## 第二部分：错误码扫盲（你问的那个）

### 什么是错误码

数据库执行 SQL 失败时，不能只吐一句人话，要返回一个**机器可判定的代号**。协议里长这样：

    {"id":3,"ok":false,"error":{"code":"duplicate_key","message":"duplicate primary key"}}

### 为什么它会影响得分

官方测试用例的预期结果文件里，会写：这条 SQL **必须失败**，并且错误语义应该是 `duplicate_key` 这一类**语义名**。

但有个坑：公开题包的 `config.json` 里 `error_codes` 是**空对象**，驱动只检查「code 是非空字符串」，所以现在**随便写什么码都能过**。

风险在于：**正式题包一旦冻结了映射表**（比如规定重复主键必须是 `duplicate_key`、表不存在必须是 `no_such_table`），码对不上就整条用例挂。

### 我们怎么处理的

内部会产生很多细粒度的码（`unsupported_statement`、`unsupported_create`、`invalid_vector`……），在 `main.cpp` 里集中做了一张**别名表**，对外统一映射：

| 内部码                                                                 | 对外码               |
| ------------------------------------------------------------------- | ----------------- |
| `unsupported_statement` / `unsupported_create` / 其他 `unsupported_*` | `unsupported_sql` |
| `no_such_table`、`duplicate_key`、`dimension_mismatch`                | 保持原样              |

好处：以后题包如果改了映射，只改这一张表，不用动执行器逻辑。

### 你回答时可以怎么说

「错误码是给机器判的语义标签。公开用例只校验非空，但正式题包可能冻结映射，所以我们在输出层做了一张别名表，把内部细码统一映射成题包口径，避免以后改一处要动全身。」

（后续我还发现实际上错误码的处理也是比较难的，由于题包里面错误码是空对象一旦题包冻结映射表就会导致码对不上使得整条用例挂掉，因此我们的处理方法为创建一个别名表进行对外的统一映射来借鉴码对不上的）

## 第四部分：要把材料从 0.5 提到高分，缺的到底是什么

官方给 0.5 分（最低档），不是格式问题——是**证据链只有半截**：有「学生提出问题」，没有「学生参与验证并得到结果」。

四个档位的判定标准：

| 档位  | 必须具备                            |
| --- | ------------------------------- |
| 0.5 | 学生提出具体问题、预测或验证方案，但**没有实际结果**    |
| 1   | 学生参与验证，并有**实际验证结果**             |
| 1.5 | 学生解释结果、据此**修正方案并复测**，形成完整证据链    |
| 2   | 在同一实例中**迁移到新场景**，完成验证，并结合结果分析局限 |

### 你现在最该补的三类内容

**A. 带数字的验证（从 0.5 → 1）**
格式：我预测 X → 让他验证 Y → 实际结果是 Z（数字）→ 所以结论是 W。
例：我以为内存要分页到磁盘很复杂，让他算 128 维 × 4 字节 = 512 字节/行，2 GiB 下几十万行就爆，实际改造后 843 MB 数据只占 85 MiB。

**B. 解释结果并修正（从 1 → 1.5）**
格式：结果超出预期/不符合预期 → 我判断原因是…… → 于是改了…… → 复测后变成……。
例：查询一开始 2.38 ms，我判断是「每次查询都把每行向量拷贝再全排序」，改成只算距离 + 有界堆后降到 0.87 ms，再加两线程后 0.13 ms。

**C. 迁移到新场景 + 分析局限（从 1.5 → 2）**
格式：同一个思路我把它用到另一个地方 → 验证也成立 → 但它有边界，边界是……。
例：「元数据常驻、内容按位置读」这套做法，我后来发现它对『过滤后 TopK』同样适用：先只读每行尾部那一行 cache line 判等值，命中才读 512 字节向量，过滤查询因此也只花 65 µs。局限是：一旦表发生 UPDATE/DELETE，快速通道会失效退回通用路径，所以它只适合读多写少的场景。

## 第五部分：五个问题的最终回答要点（在你批注基础上改）

### Q1

要点：原以为难在检索算法与崩溃一致性；实测检索不难（5.12 MB，毫秒级），真正难在**内存不能随数据量涨**（843 MB 数据 vs 85 MiB 内存）和**崩溃后的可见性判定**。

### Q2

要点：提交次数稀缺 → 提高验证标准 → 不直接采用 AI 结论 → 回原文核对 → 推翻 5 条判断（提交次数/协议形态/数据规模/题包来源）。

### Q3

要点：11/20 时 9 个失败全是 no_such_table → 定位为持久化缺失 → 接入只追加日志（带校验码 + COMMIT 标记）→ 20/20。**注意不要把它讲成「效仿 git」**。

### Q4

要点：正确性是开关不是加分项 → 先把 20 个用例做成回归护栏 → 之后每次改动必跑 → 再谈性能 → 最后材料。可用素材：6 次提交里 3 次失败都在交付链路。

### Q5

要点：先保通过拿基本分；砍 ANN（1 万行精确扫描 0.13 ms 足够快，且 ANN 有 Recall 判负风险）、砍日志压缩（短用例撑不爆）。
