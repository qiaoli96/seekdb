## 第 0 部分：这题到底要干什么（30 秒版）

做一个「迷你数据库」程序。评测程序把一条条 SQL 通过**管道**喂给它（不是网络，是标准输入输出），它执行完把结果吐回去。
要求能建表、增删改查、按向量相似度找最近邻，还要**能崩溃重启不丢数据**。

评测怎么给分：
1. **先过门槛**：官方 29 个测试用例必须**全部**通过。挂一个 → 总分 0，后面两项都不排名。
2. 过了门槛才有两项排名：**性能 40 分** + **学习材料 40 分**，都是「第一名 40 分，每低一名减 0.5」。

我们现在的位置：门槛**已经过了**；性能原始分 **2691.79**（榜首 5700+，入围预计 4600+）；材料 **0.5**（几乎没分）。

## 第 1 部分：五个你必须能讲清楚的概念

### 1.1 为什么「只有一个客户端」让事务变简单了

正常数据库要处理「很多人同时改同一行」，所以需要锁、需要多版本（MVCC），非常复杂。

但这题明确限制：**单机、单进程、单客户端、同一时刻最多一个显式事务**。也就是**永远只有一个人在操作**。

那事务还需要做什么？只剩两件事：**别丢**（说好提交的，崩溃后必须还在）、**别脏**（没提交的，崩溃后必须一点都不剩）。

所以我们的实现是：
- BEGIN 时记一个「当前文件写到哪里」的位置（不是把整库复制一份）。
- 事务里每条语句先写进日志文件尾部，但**不打 COMMIT 标记**，同时把「改之前长什么样」记在一张小的 undo 表里。
- COMMIT → 往日志里写一条 COMMIT 标记，然后**刷盘一次**。
- ROLLBACK → 按 undo 表倒着改回去，再把文件**截断**回 BEGIN 时的位置。

> 你可以这么说：因为只有一个客户端，不存在并发冲突，事务不需要锁和多版本，只需要一条判据——日志里有没有 COMMIT 标记，就决定这条数据算不算数。

### 1.2 WAL 是什么，为什么 COMMIT 就是「可见性边界」

WAL（Write-Ahead Log，预写日志）= **只往后追加、从不修改**的流水账。所有改动先记账，再谈别的。

我们日志里每条记录长这样：`[长度][校验码][事务号][类型][内容]`。

- **校验码（CRC32）**：用来发现「写到一半断电」的残记录。读到对不上校验码的记录就停，后面的当没写过。
- **COMMIT 标记**：事务的最后一条。**没有它，这个事务的所有记录都会被丢掉**。

崩溃恢复就是：从头读日志 → 攒着一堆记录 → 遇到 COMMIT 就把攒的这批正式应用 → 到文件末尾或校验失败就停。

> 你可以这么说：我们不靠「文件写成功了」判断事务成不成，只靠日志里那条 COMMIT 标记。这就是为什么「未提交的事务绝不会部分生效」——它的记录压根没有收尾标记，重放时整段被丢弃。

**我们验证过**：写完并 COMMIT 后直接 kill -9 杀进程，重启数据还在；没过 COMMIT 就杀，重启只剩旧数据。

### 1.3 为什么 843 MB 数据只占 85 MB 内存

这是这题**最反直觉**、也最值得讲的一点。

朴素做法：把所有数据读进内存里的对象 → 843 MB 数据实际要吃掉 1.5~2 GB（每个值还有额外开销）。

我们的做法：**内存里只放「目录」，不放「内容」**。
- 每行记两个数：这行在文件里的**位置**和**长度**（12 字节）
- 一张主键到行号的**索引表**（约 19 字节/行）
- 一个存活标记位（1 bit/行）

加起来约 100 MB / 288 万行。真正的内容（128 维向量 = 512 字节/行）**留在文件里，要用的时候按位置去读**。

实测：1,500,000 行 / 843 MB 数据，峰值内存 **85.4 MiB**。

> 你可以这么说：问题不是「数据放哪」，而是「什么是必须常驻的」。我们把常驻的压到只剩目录和索引，内容按需读，所以内存不随数据量线性涨。

### 1.4 L2 距离与 TopK，为什么并列要按主键排

- **向量**：128 个数组成的一个点。
- **L2 距离**：两点之间的**直线距离**（欧氏距离），先算差的平方和，再开根号。
- **TopK**：找出距离最近的 K 条。必须「精确」——不能先随便挑一批再在里面找。

两个细节容易错、也最容易被测：
1. **带过滤条件时，要先过滤再取 TopK**，不能「先在全表取 K 条再过滤」（那样结果会不够数）。
2. **距离完全相同时，按主键升序排**。这是题目硬性规定，不写就挂用例。

> 你可以这么说：距离相同的时候必须有个确定性规则，否则同样的查询两次结果不一样。题目规定按主键升序，我们就照这个排。

### 1.5 为什么「门槛 > 性能 > 材料」这个顺序是第一位的

规则写得很硬：**29 个用例挂任何一个，总分归零**，性能和材料都不排名。

所以任何「优化」都必须先过门槛。我们做优化的顺序就是：先让 20 个公开用例从 11 个过到 20 个，再谈性能。

> 你可以这么说：这题不是「做得越好分越高」，是「先及格再排名」。所以我把「用例全过」当成唯一的一号目标，性能排在它后面。

## 第 2 部分：五个问题的素材（要点和数字，不是答案）

### Q1 这题你原来以为最难的是哪块？后来发现实际难在哪？

- 一开始以为是「向量检索算法」最难（听名字像 AI 的东西）。
- 实际数据规模只有 10,000 行 × 128 维，总共 5 MB，**检索本身不难**。
- 真正难的是三件事：① 崩溃后「哪些算数」的判定；② 内存不能随数据量涨；③ 输出格式/错误码这类「差一个字节就整片挂」的细节。
- 数字：向量 5.12 MB 全扫一遍是毫秒级；而一个没写 COMMIT 的事务处理错，就直接挂一整个用例。

### Q2 「整题只提测一次」被我写错那次，你当时为什么不信？

- 我当时是**根据题面转述**下的结论，没有读原始文档。
- 你让我回到语雀原文，读完发现：**每天最多 2 次正式提交**，且「环境预检不占机会」。
- 这一个字之差直接决定策略：如果只有一次，就不敢提交未验证版本；实际每天 2 次，就可以「提一版拿反馈」。
- 同一次核对还发现另外 4 条也错了：协议其实是 JSONL 不是文本、数据规模是 1 万不是百万、题包就在 GitHub 上。

### Q3 公开用例 11 → 20，你觉得中间哪一步最关键？

- 11 个过、9 个挂，9 个失败**全都是同一个原因**：重启后查不到表（no_such_table）。
- 说明缺口唯一：**数据没落盘**。语法、类型、排序那些反而是对的。
- 把日志（WAL）接进执行器之后，9 个一次性全绿，从 11 变 20。
- 关键认识：**先看失败分布，再动手**。如果一上来就怀疑语法去改解析器，会白干。

### Q4 「29 个用例全过才有资格排名」对你安排时间有什么影响？

- 意味着**正确性是开关，不是加分项**。
- 所以顺序必须是：先把用例做到全绿 → 再谈快不快 → 最后写材料。
- 实际排法：骨架（11/20）→ 存储落盘（20/20）→ 内存可扩展 → 性能（2.38 ms → 0.39 ms）→ 材料。
- 每次改动后都重跑那 20 个用例，掉一个就立刻回退。

### Q5 如果只剩一天，你会砍掉哪部分？

- 砍 **ANN 近似索引**（HNSW/IVF）：数据只有 1 万行，精确扫描已经够快，建索引反而增加构建成本，还引入「召回率不达标」的判负风险。
- 砍 **日志压缩/合并**：日志会一直增长，但比赛跑的是短用例，不会撑爆。
- 保留：门槛相关的一切 + 材料。
- 依据：性能差 71% 是「名次差几名」的问题，门槛挂了是「0 分」的问题。

## 第 3 部分：三个你可以亲手做的验证（做完说话更有底气）

1. **看一眼日志长什么样**：`xxd -l 128 /tmp/你的数据目录/wal.log`
   前面 16 字节是文件头，后面就是一条条「长度+校验码+事务号+类型+内容」。

2. **亲手杀一次进程**：`bash tools/crash_test.sh`
   看两段输出：COMMIT 后杀 → 数据在；没 COMMIT 杀 → 数据不在。

3. **看一次内存**：`python3 /root/mvdbtest/bigtest.py 300000 1000`
   看 peak_rss_mib 是多少——数据量是内存的几倍，进程却只占几十 MB。
