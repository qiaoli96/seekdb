# 决策记录

按时间顺序记录关键取舍，每条注明依据（可核验的来源）。

## D1 性能战场不在「大库扫描吞吐」——数据规模只有 10,000×128
依据：赛题说明 3.3 节「默认 10,000 条记录、128 维向量、1,000 条 TopK 查询，K = 10，其中一半查询带普通列等值过滤」。
推论：向量总量 5.12 MB。耗时（权重 60%）由「固定开销 + 100 批提交的 fsync 次数 + 每查询一次 5 MB 扫描」决定，不由磁盘吞吐决定。

## D2 查询一律走 exact，不建近似索引
依据：Recall@10 两组（有/无过滤）均须 ≥ 0.95 才计性能分；10k 规模下精确 TopK 单次 < 1 ms。
推论：ann 换不来耗时收益，却把「索引构建」的 I/O 与峰值内存（统计窗口含构建与预热）计进去，并引入召回风险。
保留 CREATE VECTOR INDEX 的语法与语义正确性（exact 模式仍须精确），不实现真索引，除非隐藏用例逼迫。

## D3 事务用「单活动事务 + 快照 / WAL」，不做并发控制
依据：题面限定单机、单进程、单客户端、同一时刻最多一个显式事务。
推论：无锁管理器、无 MVCC 快照矩阵。

## D4 写入路径「日志即真数据」，一次提交恰好一次 fdatasync
依据：性能口径里 B 为 /data 设备的 rbytes+wbytes 增量，含装载与写回；写入项目每批 100 条且必须完成持久化后才返回，共约 100 批。
推论：双写（WAL + 数据页）会让写 I/O 翻倍；只追加一次日志可把写 I/O 压到 1×。

## D5 记录格式带长度 + CRC32，尾部半条记录必须丢弃
依据：赛题 3.2 节「已经返回 COMMIT 成功的事务必须保留；未发出提交请求的事务必须回滚；发出提交请求但未收到成功响应的事务允许完整生效或完整不生效」。
推论：commit 记录是唯一可见性边界；恢复遇到长度越界 / CRC 不匹配即截断。

## D6 输出走 JSONL，BIGINT 不经 double
依据：STDIO_PROTOCOL.md 第 3 节「BIGINT 按当前判题配置使用 JSON 整数，不能转换成字符串，也不能经浮点转换丢失精度」；公开用例 sql_bigint 专门检查超过 2^53 的范围。

## D7 本地迭代用 --command，不用 Docker
依据：protocol_check/run.py 同时支持 `--image` 与 `--command`（`{data_dir}` 占位）。
推论：功能迭代走本地二进制（秒级），Docker 只用于最终镜像验证。

## D8 行数据外存化是硬门槛，不是优化项
依据：赛题 3.2 节与 mysqltest/README 末段均要求「能处理超过内存限额的数据，不能只依赖全量常驻内存」；资源限额参考 `--cpus=2 --memory=2g`。
量级：128 维 × 4B = 512 B/行，2 GiB 限额下几十万行即触顶。
现状风险：engine.h 的 Table 用 std::vector<Row>（每值 std::string / std::vector<float>），BEGIN 时 snapshot_ = tables_ 全量深拷贝 → 峰值 2 倍。
结论：内存布局改造优先级高于性能优化——门槛不过则性能与材料双双 0 分。

## D9 错误码走「内部细码 → 对外语义码」别名表
依据：public 包 `protocol_check/config.json` 的 `error_codes` 为空对象，`_assertions.py` 只校验非空，所以现在任何非空码都能过；但正式映射冻结后会失分。
实现：main.cpp 集中一处映射，`unsupported_*` → `unsupported_sql`，`no_such_table`/`duplicate_key`/`dimension_mismatch` 保持。

## D10 性能基线（12 项实测，作为后续轮次的锚点）
口径：10,000 行 × 128 维、100 批 × 100 行写入、1,000 次 TopK（K=10，半数带等值过滤），单客户端。
实测：写入 **0.505 s**（5.05 ms/批，含每批一次 fdatasync）；查询 **2.384 s**（2.38 ms/次）；数据文件 5.62 MB。
判读：查询侧每行都要把 128 维向量拷进 Row 再全排序 10,000 条 → 明显偏离「扫描 + 堆」的量级，有 3~5 倍空间。

## D11 用「有预算的向量 arena」换查询速度，而不是无条件驻留
依据：bench 形状下每次 TopK 都要顺序扫一遍 5.6 MB 行日志（1000 次 = 5.6 GB 内存拷贝），这是 2.4 ms/次的主项；但「数据超过内存限额」又是正式要求，不能整表驻留。
决策：表的总行负载 ≤ MVDB_VEC_ARENA_MB（默认 64 MiB）时才把行镜像进 32B 对齐 slab（记录头即向量浮点，零拷贝直喂 vec::l2_distance）；估计超预算则连尝试都不做，构建中溢出则整体释放并**永久退回**流式路径。
效果：查询 0.891 → 0.389 ms/次；1.5M 行大表 RSS 85.4 MiB 不变（arena 未启用）；arena on/off 73 个快照逐字节相同。
代价：RSS ≈ 基线 + 预算（默认最坏约 141 MiB）；UPDATE 密集表垃圾累积到预算会退回流式（只损性能）。
